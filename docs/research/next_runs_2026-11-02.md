# Next run set (2026-11-02)

Goal: test the explanations from the depth anatomy and router diagnosis
(`docs/research/router_diagnosis_2026-11-01.md`) in new conditions and new models, rather than
repeat them. Account under test: extra depth fixes problem formulation, which raises per-step
reliability and compounds over long chains; per-request routing fails because the consequence of
a locally uncertain step only shows later in the chain.

## Ready (one lab job, sequential stages, ~35 h; Fable review 2026-11-02 applied: Dory cut to
480 requests after measured ~150 s per request, raw Dory answers kept so malformed calls count as
format errors, taxonomy uses the original query in every condition, 1-vs-2 draft cost charged)

| Stage | Model | What | Pre-registered analysis | Est. time |
|---|---|---|---|---|
| 1 | Ouro v3 | NESTful [0, 720) with the full gold plan in the request, 2 and 4 loops | `plan_ablation.py`: gain_none − gain_full > 0 | ~6–7 h |
| 2 | Ouro v3 | 48-token probe on BFCL single-turn (1,000 prompts); outcomes at 1–4 loops exist | `bfcl_router.py`: "4 helps" AUC lower bound > .60 | ~2 h |
| 3 | Ouro v3 | NESTful [0, 720) with only the function names given, 2 and 4 loops | `plan_ablation.py` secondary | ~6–7 h |
| 4 | Dory 1.0 4B | NESTful [0, 480), loops 1–4, greedy, reasoning off, texts and raw answers logged | `dory_replication.py`: P1 formulation, P2 compounding, P3 stability | ~20 h |

Predictions if the account is right: the full plan removes most of the 2→4 gain and its growth
with chain length; routing from early signals works better on single-turn BFCL than on NESTful;
Dory shows the same formulation/compounding/stability pattern at its main depth step (1→2).
Each outcome against the prediction is informative: a plan that does not remove the gain means
depth also buys execution reliability; routing that also fails on BFCL means the limit is not
about horizon.

The synthetic chains of `make_chains.py` were not used: their requests already state the plan
("Please X, then Y"), so they would test length without formulation; the plan-given NESTful
conditions test the same thing on the very requests the anatomy was measured on.

## New models (need a decision)

Survey (2026-11-02, model cards and papers; nothing run locally):

* **Nanbeige4.2-3B** (`Nanbeige/Nanbeige4.2-3B`, Apache-2.0, rev b82e54b): all 22 layers looped
  twice (`num_loops: 2` in config.json); the remote modeling code sizes the per-loop attention
  modules and KV slots from `config.num_loops` at load time and shares the projection weights, so
  loading with 1 or 3 loops is mechanically possible; `loop_loss_weights` is empty, so it was
  probably trained on the final loop only and 1 loop may be degenerate. Native tool calling
  (agentic post-training). Runs through `trust_remote_code` (pinned to transformers 4.42; our env
  has 5.17; a published fix list for MPS exists). Value: a tool-native looped model, zero-shot,
  for the 1-vs-2 (and 3) loop question and the anatomy.
* **Huginn-0125** (`tomg-group-umd/huginn-0125`, 3.5B, Apache-2.0): recurrent depth that re-reads
  the input each iteration, trained with random depth (mean 32), loop count a `generate`
  argument, adaptive exit built in; extra steps do not hurt per the card. Base model: needs a
  tool-trace LoRA SFT before NESTful. Value: the sharpest contrast for "gains stop at the trained
  depth" and for routing (a model trained for variable depth). Also `trust_remote_code`.
* SenseNova-Loop-9B (fixed loop count in its code), LEV checkpoints (multiple-choice decision
  heads, not generators), Parcae / Rec-OLMo (base, no instruct), LoopUS (CUDA-developed) are
  lower value for this study.

Blocker: loading either Nanbeige or Huginn executes model code downloaded from Hugging Face
(`trust_remote_code=True`). The automated permission check refused this locally; it needs the
user's explicit go-ahead (locally or as a lab job). With it, the first step is a 1-hour
feasibility check (load on MPS, one tool prompt at 1/2/3 loops for Nanbeige; `num_steps`
4/8/16/32 for Huginn), then:

1. Nanbeige zero-shot NESTful [0, 720) at loops 1, 2, 3 with texts logged (~10 h), analysed with
   `dory_replication.py`-style predictions.
2. Huginn: LoRA SFT on the chain v3 data mix (~1 day of build and training), then NESTful at
   several step counts; only if (1) and the Dory replication leave the cross-model question
   open.

Update 2026-11-12: Nanbeige4.2-3B runs only at its trained 2 loops (1 loop: gibberish; 3 loops:
breaks immediately; see progress.md). Dropped as a depth-allocation model. Huginn-0125 remains
the only candidate from another family (base model; needs a tool-calling fine-tune and
`trust_remote_code`); not pursued unless the paper needs a second family.
